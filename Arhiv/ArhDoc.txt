Файл менеджер для документов и фото в браузере. В верхнюю строку вводим путь каталога с файлами. Если каталог содержит файлы, ниже 
появляется таблица строчки с именами Слева обычная таблица с данными. Тип док-та; дальше поле с данными вводим все данные из док-та 
одной строкой через разделитель. справа окно с пустым шаблоном. данные в шаблон подтягиваются из активной строки. Справа в конце строки 
активируется кнопки: "копировать в архив. присвоить путь" "переместить в архив. присвоить путь". Данные из строки ввода, отправляются в 
базу. Файл архивируется, архив кодируется, закодированный архив помещается в защищенную директорию, а копия пересылается в облако.
Основные вводные 
Путь каталога вводится пользователем в браузере и передаётся на сервер (с валидацией, чтобы нельзя было выйти за пределы разрешённой папки).
Таблица файлов: имя, тип (документ/фото), размер, дата. При клике на строку — активация строки, подтягивание данных в шаблон справа.
Поле ввода данных: пользователь вводит данные одной строкой через разделитель (например, |). Эти данные сохраняются в БД.
Шаблон справа: простой HTML-шаблон, куда подставляются данные из активной строки.
Кнопки справа: «Копировать в архив. Присвоить путь» и «Переместить в архив. Присвоить путь». Разница: «копировать» — оригинал остаётся, 
«переместить» — файл удаляется из рабочей папки.
Архив: создаётся ZIP, кодируется (например, base64 для передачи/логики), помещается в защищённую директорию. Копия уходит в облако 
(S3/Yandex Object Storage и т.п.).
БД: запись метаданных (путь, имя, тип, данные, статус архивации, путь в архиве, ссылка в облаке).

@app.get("/api/scan")
def scan_directory(path: str):
    # ВАЖНО: валидация пути, чтобы нельзя было уйти выше разрешённого корня
    root = os.path.abspath("data/work")
    target = os.path.abspath(os.path.join(root, path.lstrip("/")))
    if not target.startswith(root):
        raise HTTPException(status_code=403, detail="Доступ запрещён")

    entries = []
    for f in os.listdir(target):
        full = os.path.join(target, f)
        if os.path.isfile(full):
            ext = f.split(".")[-1].lower()
            ftype = "photo" if ext in ["jpg", "jpeg", "png", "gif", "webp"] else "doc"
            entries.append({
                "name": f,
                "type": ftype,
                "size": os.path.getsize(full),
                "date": datetime.fromtimestamp(os.path.getmtime(full)).isoformat()
            })
    return {"files": entries}

@app.post("/api/archive")
def archive_file(
    file_name: str,
    path_input: str,
    action: str  # "copy" или "move"
):
    from app.services.archive_ops import create_and_store_archive
    from app.services.cloud_sync import upload_to_cloud

    secure_dir = "data/secure_archive"
    os.makedirs(secure_dir, exist_ok=True)

    archive_path, encoded_b64 = create_and_store_archive(
        base_path="data/work",
        sub_path=path_input,
        file_name=file_name,
        secure_dir=secure_dir,
        action=action  # copy/move
    )

    cloud_url = upload_to_cloud(archive_path)  # твоя реализация под S3/Yandex

    # Обновить запись в БД
    record = db.query(FileRecord).filter_by(file_name=file_name, path_input=path_input).first()
    if record:
        record.archived = True
        record.archive_path = archive_path
        record.cloud_url = cloud_url
        record.action_type = action
        db.commit()

    return {"archive_path": archive_path, "cloud_url": cloud_url}
Логика архивации и кодирования (archive_ops.py)
Создаём ZIP только для указанного файла (можно добавить метаданные).
Кодируем архив в base64 (это «кодирование» как ты просил; для реальной безопасности лучше использовать шифрование AES).
Сохраняем ZIP в data/secure_archive.
Если action == "move" — удаляем оригинал из data/work.
Пример:

python
import zipfile, base64, os, shutil

def create_and_store_archive(base_path, sub_path, file_name, secure_dir, action):
    src = os.path.join(base_path, sub_path, file_name)
    dst_zip = os.path.join(secure_dir, f"{file_name}.zip")

    with zipfile.ZipFile(dst_zip, "w", zipfile.ZIP_DEFLATED) as zf:
        zf.write(src, arcname=file_name)

    with open(dst_zip, "rb") as f:
        encoded_b64 = base64.b64encode(f.read()).decode("ascii")

    if action == "move":
        os.remove(src)

    return dst_zip, encoded_b64
Если нужна настоящая защита, вместо base64 используй AES-шифрование архива (библиотека cryptography).

Важные моменты безопасности и эксплуатации
Валидация путей — обязательно, иначе пользователь сможет указать ../../etc/passwd и т.д.
Изоляция папок: data/work — для просмотра, data/secure_archive — только для сервера, не отдавать напрямую через статику.
Шифрование: base64 — не шифрование. Если нужна защита, используй AES.
Облако: реализуй cloud_sync.py под S3-совместимое хранилище (Yandex Object Storage, MinIO и т.п.) — это стандарт для Cafe Offline Server.
Логирование: добавь таблицу logs с действиями (кто, когда, какой файл, какой путь, результат).

Как это стыкуется с Offline Server
Используются те же подходы: FastAPI, SQLAlchemy, файловые операции, скрипты.

Может быть несколько ссылок на один файл. К примеру если на фото сразу несколько разных документов. Или это многостраничный документ. 
Т.е. файл один, а строк в базе много.

Основные вводные 
Один физический файл (фото/скан/PDF) может содержать несколько документов/страниц, и по каждой из них пользователь хочет вести отдельную 
строку учёта (свои данные, свой шаблон, свой статус).
В БД должно быть: 1 запись о файле (метаданные, путь, архив) + N записей о «ссылках/строках» (данные, шаблон, статус архивации строки, 
связь с файлом).
Интерфейс: при выборе файла показываем список строк (документов/страниц), пользователь редактирует каждую строку отдельно, кнопки 
архивации работают на уровне строки, но физически архивируется один файл.
Логика архивации: если архивирована хотя бы одна строка — файл считается архивированным; кнопки «копировать/переместить» должны 
учитывать, что файл уже в архиве.
Изменённая структура БД (SQLAlchemy)
Разделим «файл» и «строки учёта»:

# app/db/models.py
from sqlalchemy import Column, Integer, String, DateTime, Boolean, Text, ForeignKey
from sqlalchemy.orm import relationship
from datetime import datetime
from .base import Base

class FileRecord(Base):
    __tablename__ = "files"
    id = Column(Integer, primary_key=True, autoincrement=True)
    path_input = Column(String, nullable=False)
    file_name = Column(String, nullable=False)
    full_path = Column(String, nullable=False)          # абсолютный путь к файлу
    file_type = Column(String, nullable=True)            # photo/doc/etc
    archived = Column(Boolean, default=False)             # файл целиком в архиве?
    archive_path = Column(String, nullable=True)          # путь к ZIP
    cloud_url = Column(String, nullable=True)            # ссылка в облаке
    created_at = Column(DateTime, default=datetime.utcnow)
    # Связь: один файл → много строк учёта
    rows = relationship("FileRow", back_populates="file", cascade="all, delete-orphan")


class FileRow(Base):
    __tablename__ = "file_rows"
    id = Column(Integer, primary_key=True, autoincrement=True)
    file_id = Column(Integer, ForeignKey("files.id"), nullable=False)  # ссылка на файл
    data_line = Column(Text, nullable=True)              # данные одной строкой
    template_render = Column(Text, nullable=True)       # результат подстановки в шаблон
    row_status = Column(String, default="active")        # active/archived/deleted
    row_index = Column(Integer, nullable=True)           # номер страницы/документа в файле
    action_type = Column(String, nullable=True)         # copy/move для этой строки
    created_at = Column(DateTime, default=datetime.utcnow)

    file = relationship("FileRecord", back_populates="rows")
Почему так лучше:

Один файл в files — один архив, одна загрузка в облако.
Много строк в file_rows — учёт по каждому документу/странице, свои данные и шаблоны.
Если файл удалён/перемещён, строки остаются с флагом row_status и историей.

@app.post("/api/save-row")
def save_row(
    file_name: str,
    path_input: str,
    data_line: str,
    template_content: str,
    row_index: int = None
):
    file_rec = db.query(FileRecord).filter_by(file_name=file_name, path_input=path_input).first()
    if not file_rec:
        # если файла ещё нет в БД — создаём запись о файле
        root = os.path.abspath("data/work")
        full_path = os.path.abspath(os.path.join(root, path_input.lstrip("/"), file_name))
        file_rec = FileRecord(
            path_input=path_input,
            file_name=file_name,
            full_path=full_path,
            file_type="photo" if file_name.lower().endswith(("jpg","jpeg","png")) else "doc"
        )
        db.add(file_rec)
        db.flush()  # чтобы получить file_id

    rendered = template_content.replace("{{DATA}}", data_line)

    # Если строка уже есть по row_index — обновляем, иначе создаём
    existing = db.query(FileRow).filter_by(file_id=file_rec.id, row_index=row_index).first()
    if existing:
        existing.data_line = data_line
        existing.template_render = rendered
    else:
        row = FileRow(
            file_id=file_rec.id,
            data_line=data_line,
            template_render=rendered,
            row_index=row_index,
            row_status="active"
        )
        db.add(row)

    db.commit()
    return {"file_id": file_rec.id, "rendered": rendered}
Логика архивации при множественных строках
Когда нажимают «Копировать/Переместить в архив» на строке:

Проверяем FileRecord.archived.
Если False — создаём архив (ZIP), кодируем, кладём в secure_archive, грузим в облако, ставим archived=True.
Для строки ставим row_status="archived", action_type=copy/move.
Если True — просто обновляем строку, архив не создаём повторно.
python
@app.post("/api/archive-row")
def archive_row(file_name: str, path_input: str, row_id: int, action: str):
    file_rec = db.query(FileRecord).filter_by(file_name=file_name, path_input=path_input).first()
    row = db.query(FileRow).filter_by(id=row_id).first()

    if not file_rec or not row:
        raise HTTPException(404, "Файл или строка не найдены")

    # Архивируем файл, если ещё не архивирован
    if not file_rec.archived:
        archive_path, encoded_b64 = create_and_store_archive(
            base_path="data/work",
            sub_path=path_input,
            file_name=file_name,
            secure_dir="data/secure_archive",
            action=action  # для первой строки можно взять это действие как основное
        )
        file_rec.archived = True
        file_rec.archive_path = archive_path
        file_rec.cloud_url = upload_to_cloud(archive_path)

    # Обновляем строку
    row.row_status = "archived"
    row.action_type = action
    db.commit()

    return {"archived_file": True, "cloud_url": file_rec.cloud_url}
Важно: action (copy/move) на уровне строки лучше трактовать как «тип операции, который мы применили к строке при архивации». Физически файл перемещается один раз.

from sqlalchemy import Column, Integer, String, DateTime, Boolean, Text, ForeignKey
from sqlalchemy.orm import relationship
from datetime import datetime
from .base import Base

class DocPosition(Base):
    """Учётная позиция (один документ/дело/заказ), может включать несколько файлов"""
    __tablename__ = "doc_positions"
    id = Column(Integer, primary_key=True, autoincrement=True)
    position_code = Column(String, nullable=False, unique=True)  # код/номер позиции (вручную или авто)
    data_line = Column(Text, nullable=True)                     # данные одной строкой (разделитель |)
    template_render = Column(Text, nullable=True)                # шаблон с данными
    archived = Column(Boolean, default=False)                    # позиция целиком в архиве?
    archive_path = Column(String, nullable=True)                 # путь к ZIP
    cloud_url = Column(String, nullable=True)                     # ссылка в облаке
    action_type = Column(String, nullable=True)                  # copy/move для всей позиции
    created_at = Column(DateTime, default=datetime.utcnow)

    files = relationship("DocFileLink", back_populates="position", cascade="all, delete-orphan")


class DocFileLink(Base):
    """Связь позиции с конкретным файлом (страница, приложение и т.п.)"""
    __tablename__ = "doc_file_links"
    id = Column(Integer, primary_key=True, autoincrement=True)
    position_id = Column(Integer, ForeignKey("doc_positions.id"), nullable=False)
    file_name = Column(String, nullable=False)                   # имя файла
    file_path_input = Column(String, nullable=False)             # путь, который ввёл пользователь
    full_path = Column(String, nullable=False)                   # абсолютный путь
    file_type = Column(String, nullable=True)                    # photo/doc/etc
    page_index = Column(Integer, nullable=True)                   # номер страницы (если применимо)
    is_main = Column(Boolean, default=False)                     # основной файл (для превью)
    created_at = Column(DateTime, default=datetime.utcnow)

    position = relationship("DocPosition", back_populates="files")

    root = os.path.abspath("data/work")

            file_path_input=path_input,

            file_type="photo" if name.lower().endswith(("jpg","jpeg","png")) else "doc",
            page_index=i + 1,
            is_main=(i == 0)
        )
        db.add(link)

    db.commit()
    return {"position_id": pos.id, "rendered": rendered}

@app.post("/api/archive-position")
def archive_position(position_code: str, action: str):  # action: "copy" или "move"
    pos = db.query(DocPosition).filter_by(position_code=position_code).first()
    if not pos or pos.archived:
        raise HTTPException(400, "Невалидная позиция или уже архивирована")

    secure_dir = "data/secure_archive"
    os.makedirs(secure_dir, exist_ok=True)

    archive_name = f"{pos.position_code}.zip"
    archive_path = os.path.join(secure_dir, archive_name)

    with zipfile.ZipFile(archive_path, "w", zipfile.ZIP_DEFLATED) as zf:
        for link in pos.files:
            if os.path.exists(link.full_path):
                zf.write(link.full_path, arcname=link.file_name)
                if action == "move":
                    os.remove(link.full_path)

    with open(archive_path, "rb") as f:
        encoded_b64 = base64.b64encode(f.read()).decode("ascii")

    cloud_url = upload_to_cloud(archive_path)  # твоя реализация

    pos.archived = True
    pos.archive_path = archive_path
    pos.cloud_url = cloud_url
    pos.action_type = action
    db.commit()

    return {"archive_path": archive_path, "cloud_url": cloud_url}

Итоговая модель данных (объединённая)
Тебе нужны 4 таблицы (или 3, если хочешь объединить файлы и ссылки в одну логику):

files — физический файл на диске (путь, тип, статус архивации).
file_rows — строки учёта внутри файла (для случая «одно фото → несколько документов»).
doc_positions — учётная позиция (документ/дело), которая может включать несколько файлов.
doc_file_links — связь позиции с файлами (для случая «одна позиция → несколько файлов»).
Важные связи
files ↔ file_rows: один файл → много строк.
doc_positions ↔ doc_file_links: одна позиция → много файлов.
files и doc_file_links ссылаются на одни и те же физические файлы (можно даже сделать doc_file_links.file_id → files.id, если хочешь жёсткую нормализацию).
Для старта я предложу вариант, где doc_file_links хранит full_path (чтобы можно было быстро внедрить без переделки всей структуры), но сразу закладывает возможность перехода на file_id.

    max_bytes = MAX_ARCHIVE_SIZE_MB * 1024 * 1024

    secure_dir = "data/secure_archive"
    os.makedirs(secure_dir, exist_ok=True)

    archive_name = f"{pos.position_code}.zip"
    archive_path = os.path.join(secure_dir, archive_name)

    # Если слишком большой — можно отказаться от ZIP и отправлять по отдельности
    if total_size > max_bytes:
        # Логируем: «Позиция слишком большая для единого ZIP. Отправляем файлы по отдельности»
        pos.archive_path = None
        pos.action_type = action
        db.commit()
        # Дальше логика «Вариант 3» — загрузка файлов по отдельности в облако
        return {"warning": "Позиция слишком большая. Файлы будут загружены по отдельности", "files_count": len(pos.files)}

    with zipfile.ZipFile(archive_path, "w", zipfile.ZIP_DEFLATED) as zf:
        for link in pos.files:
            if os.path.exists(link.full_path):
                zf.write(link.full_path, arcname=link.file_name)
                if action == "move":
                    os.remove(link.full_path)

    cloud_url = upload_to_cloud(archive_path)
    pos.archived = True
    pos.archive_path = archive_path
    pos.cloud_url = cloud_url
    pos.action_type = action
    db.commit()

    return {"archive_path": archive_path, "cloud_url": cloud_url}
Для Cafe Offline Server: порог можно вынести в конфиг (config.py) и менять без перекомпиляции.

Вариант 2: «Не архивировать, а загружать файлы позиции по отдельности» (самый практичный для сканов/фото)
Суть: не делаем общий ZIP. Каждый файл позиции загружаем в облако отдельно. В БД храним список ссылок на файлы в облаке.
 Логически позиция остаётся одной.

Что меняется в БД:

Убираем из doc_positions поля archive_path и cloud_url.
Добавляем в doc_file_links поле cloud_url (ссылка на конкретный файл в облаке).
В doc_positions.archived ставим True, когда все файлы позиции загружены в облако.
Плюсы:

Нет тяжёлых ZIP.
Можно быстро скачать только нужный файл (например, только чек, а не весь комплект).
Если один файл не загрузился — не теряем всю позицию.
Идеально для фото/сканов: они и так уже отдельные файлы.
Минусы: чуть сложнее логика «все ли файлы загружены», но это легко решается.

Логика архивации (по отдельности):

Что меняется:

Поле file_type в doc_file_links.
Логика архивации проверяет типы файлов и выбирает стратегию.
Плюсы: баланс между удобством и производительностью.
Минусы: больше условий, нужно тестировать.

Что делать с «кодированием» (base64)
Ты упоминал «архив кодируется». Для передачи файлов в облако не нужно кодировать в base64:

S3/Yandex Object Storage работают с бинарными файлами.
Base64 увеличивает размер на ~33% — это только ухудшит проблему «тяжёлого архива».
Base64 нужен только если ты передаёшь файл как строку в JSON/API. Для загрузки в облако используй прямой бинарный поток.
Если нужно шифрование — лучше AES поверх файла (не base64).

Логика архивации «по отдельности» с путём C:\Arhiv
Суть: для каждой позиции мы не делаем один большой ZIP. Вместо этого:

Каждый файл позиции копируем/перемещаем в C:\Arhiv (с сохранением структуры или плоским списком).
Каждый файл отдельно грузим в облако.
В doc_file_links.cloud_url пишем ссылку на конкретный файл.
Когда все файлы позиции загружены — ставим doc_positions.archived = True.
Эндпоинт FastAPI (вариант «отдельные файлы», без тяжёлого ZIP)
python
import os
import shutil
from pathlib import Path
from fastapi import FastAPI, HTTPException
from sqlalchemy.orm import Session

app = FastAPI()
ARCHIVE_ROOT = r"C:\Arhiv"
os.makedirs(ARCHIVE_ROOT, exist_ok=True)

@app.post("/api/archive-position-split")
def archive_position_split(position_code: str, action: str = "copy"):
    """
    action: "copy" — оставить оригинал, "move" — удалить оригинал после архивации
    """
    pos = db.query(DocPosition).filter_by(position_code=position_code).first()
    if not pos:
        raise HTTPException(404, "Позиция не найдена")

    uploaded_count = 0
    for link in pos.files:
        src = Path(link.full_path)
        if not src.exists():
            continue

        # Формируем путь в архиве: C:\Arhiv\DOC-001\filename.jpg
        archive_subdir = Path(ARCHIVE_ROOT) / pos.position_code
        archive_subdir.mkdir(parents=True, exist_ok=True)
        dst = archive_subdir / src.name

        if action == "move":
            shutil.move(str(src), str(dst))
        else:
            shutil.copy2(str(src), str(dst))

        link.archive_path = str(dst)

        # Загрузка в облако (один файл, без ZIP)
        cloud_url = upload_to_cloud(str(dst))  # твоя функция
        link.cloud_url = cloud_url

        uploaded_count += 1

    all_uploaded = uploaded_count == len(pos.files)
    pos.archived = all_uploaded
    pos.action_type = action
    db.commit()

    return {
        "position_code": position_code,
        "files_processed": uploaded_count,
        "all_uploaded": all_uploaded,
        "archive_root": ARCHIVE_ROOT
    }
Почему это решает проблему «тяжёлый архив»:

Нет одного ZIP на сотни мегабайт: каждый файл — отдельно.
Если сеть «просядет» на одном файле — остальные всё равно уйдут.
Можно скачать только нужный файл (чек, накладную и т.п.), а не весь комплект.
C:\Arhiv остаётся локальным хранилищем, а облако — резервной копией.
Если ты всё-таки хочешь иногда делать ZIP (но безопасно)
Если для каких-то позиций нужно собрать ZIP (например, комплект PDF), делай это только если суммарный размер небольшой (например, 
до 50–100 МБ) и сразу клади в C:\Arhiv:

python
import zipfile

MAX_ARCHIVE_SIZE_MB = 100

def try_make_zip_for_position(position_code: str):
    pos = db.query(DocPosition).filter_by(position_code=position_code).first()
    total_size = sum(
        os.path.getsize(l.full_path) for l in pos.files if os.path.exists(l.full_path)
    )
    max_bytes = MAX_ARCHIVE_SIZE_MB * 1024 * 1024

    if total_size > max_bytes:
        return None  # не делаем ZIP, используем split-вариант

    archive_dir = Path(ARCHIVE_ROOT) / pos.position_code
    archive_dir.mkdir(parents=True, exist_ok=True)
    zip_path = archive_dir / f"{pos.position_code}.zip"

    with zipfile.ZipFile(zip_path, "w", zipfile.ZIP_DEFLATED) as zf:
        for link in pos.files:
            src = Path(link.full_path)
            if src.exists():
                zf.write(src, arcname=src.name)

    cloud_url = upload_to_cloud(str(zip_path))
    return str(zip_path), cloud_url
